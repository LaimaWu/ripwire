### Added — `--for` shows how a shown Python def is registered through a manifest entry point

When a ranked row of a `--for` answer is a Python definition that a manifest entry point names, the answer now carries the registration after the file tail: `<ep p= l= group=>` for the manifest group (setup.cfg `[options.entry_points]`, pyproject.toml `[project.entry-points.*]`, `[project.scripts]`, `[project.gui-scripts]`, `[tool.poetry.plugins.*]`, `[tool.poetry.scripts]`), each entry as written with the in-tree definition it names (`def=file:line`, else `external="1"` or `unresolved="1"`), and `used_at=`/`used_in=`: the code that compares or loads the group's string literal (`ep.group == "…"`, `entry_points(group=…)`, `.select(group=…)`, `iter_entry_points(…)`, `entry_points()[…]`), matched by literal text, not resolved. A group no code reads carries no `used_at=`. Default regime and XML only (`--json`, `--token-budget=N`, `--signatures-only`, `--detail=N` unchanged); `RIPWIRE_NO_EP_MANIFEST=1` turns it off. Not read: setup.py `entry_points={…}`, package.json `bin`/`exports`, pyproject inline tables, multi-root runs. On flake8's "how is a formatter registered" question the answer now names setup.cfg and the loader `_classify_plugins` (+1.3 KB); the other in-sample answers measured are unchanged unless a shown row is an entry-point target. The gap was found by comparing answers with graphify (Apache-2.0); the mechanism here is ripwire's own, no code was taken from it.
